## What / When

Filters add a popover next to the search box. Use them on **Doctrine server-side** tables when users
need structured criteria (status, date range, free text) beyond global search.

They do not apply to client-side inline datasets in this version.

## Minimal Example

Declare filters on your `AbstractDataTable`:

```php
use Pentiminax\UX\DataTables\Filter\ChoiceFilter;
use Pentiminax\UX\DataTables\Filter\TextFilter;
use Pentiminax\UX\DataTables\Model\Filters;

public function configureFilters(Filters $filters): Filters
{
    return $filters
        ->add(TextFilter::new('email')->label('Email'))
        ->add(
            ChoiceFilter::new('status')
                ->label('Status')
                ->options(['Draft' => 'draft', 'Published' => 'published'])
        );
}
```

Or declare them on the class holding the data, with no `configureFilters()` at all:

```php
use Pentiminax\UX\DataTables\Attribute\DataTableFilter;

class User
{
    #[DataTableFilter(options: ['label' => 'Email'])]
    private string $email;

    #[DataTableFilter(options: ['label' => 'Status'])]
    private Status $status;
}
```

The filter class is guessed from the declared type, and a `BackedEnum` brings its own options along.

## Pitfalls

<Aside type="caution">
  Enable `serverSide()` first. Filters send criteria over Ajax and apply Doctrine conditions in the
  query pipeline.
</Aside>

<Aside type="caution">
  `configureFilters()` wins over `#[DataTableFilter]` wholesale rather than merging with it. One
  filter declared in PHP means the attributes are not read at all.
</Aside>
