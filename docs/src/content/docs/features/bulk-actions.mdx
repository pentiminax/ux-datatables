Bulk actions let a user select rows and run a single PHP handler over all of them. Declare them in
`configureBulkActions()`; the bundle adds the checkbox selection, the **Bulk actions** button above
the table, and the endpoint that executes the handler.

## Declaring Bulk Actions

```php
use App\Entity\Order;
use App\Service\OrderApprover;
use Pentiminax\UX\DataTables\Attribute\AsDataTable;
use Pentiminax\UX\DataTables\Column\NumberColumn;
use Pentiminax\UX\DataTables\Column\TextColumn;
use Pentiminax\UX\DataTables\Enum\Icon;
use Pentiminax\UX\DataTables\Model\AbstractDataTable;
use Pentiminax\UX\DataTables\Model\BulkAction;
use Pentiminax\UX\DataTables\Model\BulkActions;
use Pentiminax\UX\DataTables\Model\DataTable;
use Pentiminax\UX\DataTables\Mutation\BulkActionContext;
use Pentiminax\UX\DataTables\Mutation\BulkRecords;

#[AsDataTable(Order::class)]
final class OrdersDataTable extends AbstractDataTable
{
    public function __construct(private readonly OrderApprover $approver)
    {
    }

    public function configureDataTable(DataTable $table): DataTable
    {
        return $table->serverSide();
    }

    public function configureColumns(): iterable
    {
        yield NumberColumn::new('id', 'ID');
        yield TextColumn::new('reference', 'Reference');
        yield TextColumn::new('status', 'Status');
    }

    public function configureBulkActions(BulkActions $actions): BulkActions
    {
        return $actions->add(
            BulkAction::new('approve', 'Approve')
                ->icon(Icon::Check)
                ->askConfirmation('Approve {count} orders?')
                ->setPermission('ORDER_APPROVE', static fn (Order $order): Order => $order)
                ->successMessage('Orders approved.')
                ->handler(function (BulkRecords $records, BulkActionContext $context): void {
                    foreach ($records as $order) {
                        $this->approver->approve($order);
                    }
                })
        );
    }
}
```

The table is a service, so the handler closure captures whatever the table injected. The bundle
never calls an application URL: the handler runs inside the bundle's endpoint.

## What the User Sees

A **Bulk actions** button sits in the table's top-right layout cell. It is always rendered and stays
disabled until a row is checked; clicking it opens a dropdown listing the configured actions.

Below the toolbar row, a full-width band shows the current selection — `5 records selected` on the
left, `Select all 50` and `Deselect all` on the right. After a run it shows the processed and
skipped counts, or, when the run fails, the endpoint's message (`bulk.bar.failed` when it gives
none); the next selection change brings the count back. Move the button with
`BulkActions::position()`; the band follows it.

Declaring a bulk action also enables the Select extension in `multi` style with a checkbox column
and a header checkbox, unless the table configures one itself. A bundle-wide
`data_tables.extensions.select` default does not count as the table's own choice: it is replaced
for tables that declare bulk actions. Configuring `SelectStyle::SINGLE` on the table alongside bulk
actions throws — a bulk action over one row is a row action.

When the current user may run none of the declared actions, the button disappears, and so do the
checkboxes the bundle added for them. A Select extension the table configured itself stays.

## What the Handler Receives

`BulkRecords` yields the selected entities lazily, chunk by chunk, so a selection of 50,000 rows
never materializes as 50,000 objects. It is `Countable` and `IteratorAggregate`, plus `map()`,
`filter()`, `first()`, `isEmpty()` and `toArray()`.

<Aside type="caution">
  `count()` reports the number of **selected** rows, which is known before anything is loaded. Rows
  that no longer exist, and rows the user may not act on, are skipped during iteration. Read
  `BulkActionContext::processedCount()` and `skippedCount()` after iterating for the real numbers.
  `BulkRecords` can only be iterated once.
</Aside>

`BulkActionContext` carries `entityClass`, `dataTableClass`, `action`, `objectManager`,
`selectedCount`, and the two running counters above.

## Selecting Every Matching Row

By default the bar offers to extend the selection to every row matching the current search, filters
and ordering — not just the current page. The browser then sends the DataTables request it was
displaying, and the server re-runs it without pagination to resolve the identifiers, minus the rows
unchecked afterwards.

This requires a data provider implementing `IdentifierCollectingDataProviderInterface`;
`DoctrineDataProvider` does. The provider is asked for the field the selection speaks in — the one
written as `DT_RowId`, which `setIdField()` may point away from the primary key — so a custom
implementation must answer with values from that field. A table that calls `highlightUpdates()` writes
`DT_RowId` from its `idField` instead. Either way, that field must be a mapped, unique Doctrine field:
the rows are loaded back by its values, so a value shared by several rows would pull in every one of
them, including rows outside the current search and filters. Any other provider answers `400` for a select-all, and so does a table
declaring `selectCurrentPageOnly()`.

## Authorization

Every bulk action goes through `Permission::DT_EXECUTE_ACTION`, exactly like a row action:

- a **static** permission (`setPermission('ORDER_APPROVE')`) is checked twice — once while rendering,
  so a denied action is never drawn, and once in the endpoint before any entity is loaded;
- a **per-row** permission (`setPermission('ORDER_APPROVE', fn (Order $o) => $o)`) is checked for
  each loaded entity. Denied rows are excluded from the handler and counted as skipped; the run is
  not aborted.

```php
use Pentiminax\UX\DataTables\Model\BulkAction;
use Pentiminax\UX\DataTables\Security\ActionPermissionContext;
use Symfony\Component\Security\Core\Authorization\Voter\Voter;

final class OrderBulkVoter extends Voter
{
    protected function supports(string $attribute, mixed $subject): bool
    {
        return $subject instanceof ActionPermissionContext && $subject->action instanceof BulkAction;
    }
}
```

<Aside type="caution">
  The selection is client-side data: the browser sends row identifiers, and nothing else vouches for
  them. The endpoint re-authorizes every entity it loads, but it is still an Ajax route of your
  application — protect it with your own `security.firewalls` configuration, like every other one.
  See [Securing Ajax Routes](/ux-datatables/getting-started/security/).
</Aside>

## Ajax Endpoints

`POST /datatables/ajax/bulk` — body: `dataTable` (the signed action token), `action` (the action
name), `ids`, `allMatching`, `deselectedIds`, `query` (the displayed DataTables request, only for a
select-all). The CSRF token travels in the `X-CSRF-Token` header.

The response is `{"success": true, "processed": n, "skipped": m}`.

<Aside type="note">
  A run is not a single transaction: each chunk is flushed on its own, so a chunk that throws leaves
  the preceding ones committed. The client reloads the table either way, so it always shows what
  actually happened.
</Aside>

## Events

The table element dispatches `datatables:bulk:start` before the request, then
`datatables:bulk:success` or `datatables:bulk:error`. Each carries the action name; `start` adds the
selection, `success` the parsed response, and `error` either the refused response or the network
error:

```javascript
this.element.addEventListener('datatables:bulk:success', (event) => {
  const { action, result } = event.detail
  console.info(`${action}: ${result.processed} processed, ${result.skipped} skipped`)
})
```

## Translations

The chrome is translated server-side from the `DataTables` catalog: `bulk.bar.trigger` (the button
label), `bulk.bar.selected`, `bulk.bar.selectAllMatching`, `bulk.bar.allMatchingSelected`,
`bulk.bar.clear`, `bulk.bar.confirm`, `bulk.bar.cancel`, `bulk.bar.processed`,
`bulk.bar.skipped` and `bulk.bar.failed`. The count-bearing ones accept a `{count}` placeholder.
